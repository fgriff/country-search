# Документация Country Search Application

## 1. Механизм отмены устаревших запросов

Для решения проблемы «гонки запросов» (когда ответ на старый запрос приходит позже, чем на новый, и перезаписывает актуальные данные) в приложении используется **реальная отмена запросов** через `AbortController`, а не фильтрация результатов по флагу или таймстампу.

**Почему выбран `AbortController`, а не флаг «актуальности»?**

1. **Экономия ресурсов:** При использовании флага сетевой запрос продолжает выполняться в фоне, потребляя трафик и ресурсы сервера. `AbortController` отправляет сигнал отмены на уровень сети, прерывая соединение.
2. **Предотвращение микро-гонок:** Даже если проверка флага происходит перед рендером, существует вероятность, что ответ уже начал обрабатываться. Отмена на уровне `fetch` гарантирует, что промис будет отклонен с `AbortError` и не попадет в `then`.
3. **Прозрачность:** В DevTools (вкладка Network) отмененные запросы помечаются как `canceled`, что упрощает отладку и доказывает корректность работы приложения.

**Как это устроено в коде:**

1. При каждом изменении ввода (в методе `onInput` контроллера) проверяется наличие активного `AbortController` от предыдущего запроса. Если он есть, вызывается `abort()`.
2. Важно: отмена происходит **сразу при вводе**, а не в момент срабатывания `debounce`. Это предотвращает ситуацию, когда устаревший запрос успевает завершиться за время задержки `debounce`.
3. Для каждого нового запроса создается новый `AbortController`, и его сигнал передается в `searchCountries`.
4. В `searchCountries` сигнал отмены пользователя объединяется с сигналом таймаута через `AbortSignal.any([signal, AbortSignal.timeout(ms)])`. Это позволяет прерывать запрос как по инициативе пользователя, так и по истечении времени.

## 2. Обоснование задержки debounce

В приложении используется задержка `debounce`, равная **300 мс**.

**Почему выбрано именно 300 мс?**

- **Если убрать задержку (0 мс):** Запрос будет отправляться на каждое нажатие клавиши. Это создаст огромную нагрузку на API, увеличит количество отмен и может привести к временной блокировке (rate limiting) со стороны сервера. Кроме того, это увеличивает шанс возникновения гонок.
- **Если сильно увеличить задержку (например, 1000 мс):** Интерфейс будет казаться «тормозным». Пользователь наберет слово, но результаты появятся только через секунду, что создает ощущение неотзывчивости.
- **300 мс** — это золотая середина, проверенная UX-исследованиями. Пользователь успевает набрать слово или его часть, а приложение реагирует достаточно быстро, чтобы казаться «живым».

## 3. Вычислительная сложность (Big O)

- **`mapCountryResponse`**:
  Функция принимает массив стран и преобразует его через `.map()`.
  **Сложность: O(N)**, где N — количество стран в ответе. Массив проходится один раз, выполняя O(1) операций для каждого элемента (доступ к полям, `map` для языков и валют). Поскольку API возвращает небольшое количество стран на один запрос, это не является узким местом.

- **`debounce`**:
  Использует замыкание и `setTimeout`.
  **Сложность: O(1)** на каждый вызов (просто сброс таймера).

- **`classifyError`**:
  Использует `instanceof` и проверки строк.
  **Сложность: O(1)**.

- **Кэш и дедупликация (`cache.ts`)**:
  - **Доступ к закэшированным результатам (Map.get/set):** **O(1)**. Поиск по строке запроса происходит мгновенно, что делает повторные запросы практически бесплатными по времени.
  - **Дедупликация (Promise.race):** **O(1)**. Если запрос уже в полете, возвращается существующий промис, новые сетевые запросы не создаются.
  - **Обновление счетчика слушателей (RefCounting):** **O(1)**. При отмене или добавлении нового слушателя число инкрементируется или декрементируется.

- **История поиска (`history.ts`)**:
  - **Чтение/запись (JSON.parse/stringify):** **O(K)**, где K — количество элементов в истории (ограничено 10). Так как K — константа, сложность можно считать **O(1)**.
  - **Фильтрация дубликатов (`filter`):** **O(K)**. Проход по массиву фиксированной длины.

## 4. Применение принципов чистого кода

В проекте использованы следующие принципы:

1. **Single Responsibility Principle (SRP):**
   - Каждый модуль отвечает за свою задачу. `searchCountries` только делает запрос, `mapCountryResponse` только преобразует данные, `classifyError` только классифицирует ошибки. UI разделен на отдельные файлы (`loading.ts`, `error.ts`, `modal.ts` и т.д.).

2. **Pure Functions (Чистые функции):**
   - `mapCountryResponse` — не имеет побочных эффектов, возвращает новый объект, не мутирует входные данные. Легко тестируется без моков.
   - `classifyError` — детерминирована и не зависит от внешнего состояния.

3. **Immutability (Неизменяемость):**
   - В `mapCountryResponse` используется `??` и методы `map`, которые создают новые массивы, вместо мутации исходного `raw`-объекта.
   - В `SearchController` состояние не мутируется напрямую, а передается в колбэк `onStateChange` в виде нового объекта `AppState` (дискриминированного юниона).

4. **Discriminated Unions (Дискриминированные юнионы):**
   - Тип `AppState` описывает все возможные состояния UI (`idle`, `loading`, `success`, `empty`, `error`). TypeScript гарантирует обработку всех случаев в `switch` и не позволяет обратиться к полю `data` в состоянии `loading`.

5. **Function Composition (Композиция):**
   - Функция `createSearchController` объединяет в себе `debounce`, `searchCountries` и `classifyError`, инкапсулируя сложность и предоставляя наружу простой интерфейс `{ onInput, retry }`.

6. **Отсутствие DOM-логики в ядре:**
   - Весь слой `core/` не зависит от браузера. Он тестируется в среде Node.js/jsdom без использования реального DOM, что доказывает его переносимость и чистоту.

## 5. Бонусная архитектура: Кэш, Дедупликация и Отмена

Реализация кэша (в `src/core/cache.ts`) решает сразу две задачи: экономию трафика и предотвращение дублирующих запросов. Однако интеграция кэша с отменой (`AbortController`) создает свою проблему.

**Проблема:**
Если два компонента запрашивают `spain`, им возвращается один и тот же промис. Если первый компонент вызовет `abort()`, промис отклонится для обоих. Это нарушает требование ТЗ: _"отмена запроса одним из них не должна рушить этот промис для остальных"_.

**Решение (RefCounting):**

1. Кэш хранит не только промис, но и `AbortController`, а также счетчик активных слушателей (`listenersCount`).
2. Когда происходит запрос данных, счетчик увеличивается. Каждый вызывающий получает свой собственный `Promise.race` (между результатом кэша и своим сигналом отмены).
3. Если один из вызывающих отменяет запрос, его промис отклоняется с `AbortError`, но **счетчик уменьшается**. Если счетчик становится равен 0 (все пользователи отменили запрос), кэш вызывает `abort()` на **своем** контроллере, и реальный сетевой запрос отменяется (в Network tab появляется `(canceled)`).
4. Если запрос успешно завершается, результат сохраняется в `Map` (для мгновенной отдачи при повторном запросе), а слушатели получают данные.

Данный подход гарантирует, что кэш не «протекает», отмены работают корректно, а пользователи не блокируют друг друга.
